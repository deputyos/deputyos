# Run deputyOS locally (Docker "remote" + desktop installer)

Run the whole deputyOS stack on one laptop: a Docker-hosted "remote" — the
release **CDN** *and* the accounts/tunnel/backup **API** — that the
**desktop installer** (`deputyos-desktop`) pulls from, booting a real
`qemu-x86_64` VM locally. The booted image's agent talks to the local Docker
API instead of `api.deputyos.com`, so you can exercise the full
install → wizard → tunnel/accounts loop with zero external dependencies.

This is the end-to-end developer loop. It composes the existing
build → sign → manifest → publish pipeline with a local CDN service and the
desktop launcher, and wires the booted VM at the local API via a cloud-init
seed.

## Architecture

```
+-------------------+      manifest.json + signed qcow2 + signed launcher
|  make             |      (dist/, served by nginx)
|  desktop-local-   |                                              +------------------+
|  build            |──────────► dist/ ──► docker cdn (:8090) ──────►| deputyos-desktop  |
|  (build+sign+     |                                              |  install         |
|   manifest+publish)                                              |  start           |
+-------------------+                                              +--------+---------+
                                                                            │
                                                                   qemu-x86_64 VM (KVM)
                                                                   wizard :7088 ──► browser
                                                                            │
                                                            cloud-init seed ISO injects
                            +-----------------------+    DEPUTYOS_API_BASE=http://10.0.2.2:3000
                            | docker api (:3000)    |◄─────────────────────────────────────┐
                            |   accounts/tunnel/    |          (10.0.2.2 = qemu user-net      │
                            |   backup/audit        │           host gateway = your laptop)  │
                            +-----------------------+              in-VM agent calls ────────┘
                            | docker www (:4321)    |
                            +-----------------------+
```

| Port | Service | What it is |
|---|---|---|
| `:8090` | `cdn` (nginx) | serves `dist/` — the signed manifest + images + launcher |
| `:3000` | `api` | the accounts/tunnel/backup/audit API (from `../api-deputyos-com`) |
| `:4321` | `www` | the marketing/docs site (from `../www-deputyos-com`) |
| `:7088` | wizard | in-VM first-boot wizard, host-forwarded to the guest's `:8088` |
| `:7080` | gateway | in-VM chat/relay, host-forwarded to the guest's `:8080` |

The `:7088`/`:7080` **host-side** forwards (guest wizard + relay stay on
`:8088`/`:8080`) are env-overridable — `DEPUTYOS_DESKTOP_WIZARD_PORT` /
`DEPUTYOS_DESKTOP_GATEWAY_PORT` (defaults `7088`/`7080`). The loop uses the 7000
series by default because dev hosts frequently have stale processes squatting
on `8088`/`8080`, which silently breaks qemu's port forward.

The dev minisign key (`~/.config/deputyos/dev-keys/deputyos-dev.{key,pub}`,
auto-generated by `make sign-dev`) is the same key the launcher verifies
against (`deputyos-desktop::config::pubkey_path()`), so trust aligns without
any real code-signing cert.

## Prerequisites

```sh
make doctor   # certifies the toolchain
```

`make desktop-local-build` and `make desktop-local` run a **preflight** that
fails fast with per-tool install hints if any loop prerequisite is missing —
so you find out *before* the slow Packer build, not 15 minutes into it.

You need, beyond the standard build prereqs:

- **Docker** + `docker compose` — runs the cdn/api/www stack. Also needed
  at *build* time (`make desktop-local-build`) when your build host's glibc
  is newer than the image's (Debian Bookworm, glibc 2.36): on such hosts
  `build.sh` builds the in-guest binaries (`deputyctl`, `deputywizard`) inside
  a `rust:1.91.1-bookworm` container so they link glibc 2.36 and run in the
  VM. Hosts with glibc ≤ 2.36 (typical CI) build on the host and don't need
  Docker for the binary build. Override with
  `DEPUTYOS_GUEST_BIN_BUILD=host|container`.
- **`qemu-system-x86_64`** — the launcher boots the VM with it (+ `/dev/kvm`
  for speed; falls back to TCG if absent). Install: `sudo apt install
  qemu-system-x86` (Debian/Ubuntu).
- **`minisign`** — signs + verifies artefacts. Install: `sudo apt install
  minisign` or build from [jedisct1/minisign](https://github.com/jedisct1/minisign).
- **One ISO builder**: `cloud-localds` *or* `genisoimage` *or* `xorriso` —
  builds the cloud-init seed ISO. Install: `sudo apt install cloud-image-utils`
  (provides `cloud-localds`) — the simplest option.
- **`packer`** + **`ansible`** — only for the *first* image build (the qcow2);
  reused on subsequent runs. `make doctor` checks these.
- **Sibling repos** checked out beside this repo:
  - `../api-deputyos-com` — the API service source.
  - `../www-deputyos-com` — the www site source.

## The one-command loop

```sh
# 1. Build the image + launcher, sign, manifest, publish to dist/.
make desktop-local-build

# 2. Start the Docker "remote": cdn (:8090) + api (:3000) + www (:4321).
make cdn-up

# 3. Install + start the VM, wired at the local API. Opens the wizard.
make desktop-local
```

`make desktop-local-build` runs (in order):

1. `make build TARGET=qemu-x86_64 PROFILE=openclaw` — **only if**
   `build/qemu-x86_64-openclaw.qcow2` is missing (Packer, slow first run ~10+ min
   and needs network; reused thereafter).
2. Symlink the Packer output name to the manifest-conforming name so
   `scripts/manifest.sh`'s filename regex matches (see [Troubleshooting](#troubleshooting)).
3. `make desktop-launcher-release` — build + stage the host-triple launcher.
4. `make sign-dev` — sign the qcow2 + launcher with the dev minisign key.
5. `make publish-local` — emit `dist/manifest.json` (artefacts +
   `desktop_launchers`) + mirror to `dist/<version>/` for the cdn to serve.

`make desktop-local` runs `scripts/desktop-local.sh`, which:

1. Builds a NoCloud cloud-init seed ISO whose `write_files` drops
   `DEPUTYOS_API_BASE=http://10.0.2.2:3000` into a systemd
   `DefaultEnvironment` drop-in (covers `deputyos-tunnel` + `deputywizard`, which
   don't source `secrets.env`) **and** into `/etc/deputyos/secrets.env`
   (covers the gateways, which `EnvironmentFile` it).
2. Points the launcher at `http://localhost:8090/manifest.json` + the dev
   pubkey.
3. Runs `deputyos-desktop install` (download + sha256 + minisign verify the
   qcow2 from the CDN) and `deputyos-desktop start` (boot qemu with the seed
   attached; the LinuxDriver honors `DEPUTYOS_DESKTOP_SEED_ISO`).

The wizard opens at <http://localhost:7088> (host forward to the guest's
`:8088`; first boot takes ~30–60s for cloud-init + the wizard restart). From
inside the VM, the agent's accounts/tunnel/backup/audit calls hit
`10.0.2.2:3000` — your laptop's Docker `api`, visible via
`docker compose -f docker-compose.dev.yml logs -f api`.

## Re-running after a code change

- **Launcher code changed** (anything under `deputyos-desktop/`): the launcher
  is rebuilt by `desktop-launcher-release`; just re-run `make desktop-local-build
  && make desktop-local`. `install` is a no-op if the qcow2 is unchanged;
  `self-update` would also pick up the new launcher from the manifest.
- **Image/appliance code changed** (roles, deputyctl, deputywizard baked in):
  delete the cached qcow2 to force a Packer rebuild, then re-run the loop:
  ```sh
  rm build/qemu-x86_64-openclaw.qcow2
  make desktop-local-build && make cdn-up && make desktop-local
  ```
  (also wipe the launcher's cache so `install` re-pulls:
  `rm -f ~/.cache/deputyos-desktop/deputyos-qemu-x86_64.qcow2*`).
- **API or www changed**: `make cdn-down && make cdn-up` (compose rebuilds the
  images from the sibling repos).

## Teardown

```sh
target/release/deputyos-desktop stop   # or: make cdn-down stops the stack too
make cdn-down                          # stop cdn + api + www
```

## Troubleshooting

- **Wizard URL shows a file listing / "Connection refused" / a different
  app** — a stale host process is squatting the wizard's host port, so qemu's
  `hostfwd` couldn't bind it (qemu warns `Could not redirect host port …` to
  stderr, which the launcher discards). The loop defaults to `:7088`/`:7080`
  to avoid this, but if something still holds them: `ss -tlnp | grep -E ':7088|:7080'`
  to find the PID, kill it (`fuser -k 7088/tcp`), then re-run `make desktop-local`.
  You can also move the loop off the conflict entirely with
  `DEPUTYOS_DESKTOP_WIZARD_PORT=7188 DEPUTYOS_DESKTOP_GATEWAY_PORT=7180 make desktop-local`.
- **Wizard loads but shows an "Unauthorized" page** — the baked
  `deputywizard.service` runs `--production` (single-use token auth), so a bare
  tokenless URL gets `page_unauthorized()`. The seed drops a
  `deputywizard.service.d/no-token.conf` override switching the wizard to
  `--no-token` (no auth gate, `--production` apply mode kept) and `runcmd`
  restarts it — but on first boot there's a brief window before that restart
  lands. Wait a few seconds and refresh. If it persists, the seed didn't apply:
  wipe the cached image for a clean first boot
  (`rm -f ~/.cache/deputyos-desktop/deputyos-qemu-x86_64.qcow2*`) and re-run.
- **`manifest.sh: no artefacts matched …; nothing to manifest`** — the
  conforming-name symlink wasn't created, so the qcow2 was skipped. Re-run
  `make desktop-local-build` (step 2 creates the symlink). If you build the
  qcow2 by hand, ensure a `build/deputyos-<profile>-qemu-x86_64-<version>-<channel>.qcow2`
  exists (or symlink it from `build/qemu-x86_64-<profile>.qcow2`).
- **`error: need one of cloud-localds, genisoimage, xorriso`** — install an
  ISO builder (see [Prerequisites](#prerequisites)); the seed can't be built
  without one.
- **`error: minisign not installed`** — install minisign; `make sign-dev`
  needs it to sign artefacts.
- **The wizard opens but the agent still hits `api.deputyos.com`** — the
  seed didn't apply. Confirm the seed ISO was attached (`DEPUTYOS_DESKTOP_SEED_ISO`
  set) and that the VM is on its *first* boot with this seed (NoCloud runs
  `write_files` once per `instance-id`; a re-booted VM won't re-apply it — wipe
  the launcher cache and `install` fresh to get a clean first boot).
- **`10.0.2.2:3000` unreachable from the VM** — the Docker `api` service
  publishes on `0.0.0.0:3000` by default, reachable at the qemu user-net
  gateway. If you overrode the compose port binding to `127.0.0.1:3000:3000`,
  the guest can't reach it; use `3000:3000`. Override the target via
  `DEPUTYOS_LOCAL_API=http://10.0.2.2:<port>` when running `make desktop-local`.
- **`dev key missing at …`** — run `make sign-dev` once to auto-generate the
  dev keypair before `make desktop-local`.
- **`deputywizard: GLIBC_2.xx not found` in `~/.cache/deputyos-desktop/qemu.log`,
  deputywizard crash-loops, wizard never comes up** — the in-guest binaries
  were built against a newer glibc than the Bookworm image (2.36) has. This
  happens when the build host's glibc is newer (e.g. pop-os/Ubuntu 25.04,
  glibc 2.39) and the container build path didn't run. Confirm Docker is
  available at build time and re-run `make desktop-local-build` (it should
  log `building deputyctl in rust:1.91.1-bookworm`); or force it with
  `DEPUTYOS_GUEST_BIN_BUILD=container make desktop-local-build`. The staged
  binaries max out at `GLIBC_2.34` and run on the image. You must delete the
  cached qcow2 to re-bake with the new binaries:
  `rm build/qemu-x86_64-openclaw.qcow2` (see [Re-running](#re-running-after-a-code-change)).
- **`[UFW BLOCK] … DPT=8088` in `qemu.log`, wizard unreachable from the host
  but the guest is up** — the baked ufw profile permits the wizard only on
  loopback, so the host's qemu `hostfwd` traffic (arriving on the user-net
  NIC `enp0s2` from `10.0.2.2`) is dropped. The seed opens 8088/8080 on
  `enp0s2` via `runcmd` (instance-id v3), so a clean first boot fixes it. If
  it persists, the seed is stale — wipe the launcher cache
  (`rm -f ~/.cache/deputyos-desktop/deputyos-qemu-x86_64.qcow2*`) and re-run
  `make desktop-local` for a fresh first boot.
- **`deputywizard` crash-loops with `Error: loading providers catalogue …
  reading providers from deputyctl/etc/providers.json … No such file or
  directory`, wizard never comes up** — the image is missing
  `/etc/deputyos/providers.json` (the provider catalogue `deputywizard` reads at
  boot via `deputyctl::paths::providers_file()`). The build is supposed to copy
  `deputyctl/etc/providers.json` there (see the doc in `deputyctl/src/model.rs`),
  but an image baked before that staging ran ships without it and the wizard
  exits before binding `:8088`. Re-bake from a current checkout (`make
  desktop-local-build` stages + the role asserts providers.json is present, so
  a missing stage now fails the build loudly instead of producing a broken
  image): `rm build/qemu-x86_64-openclaw.qcow2 && make desktop-local-build`.
  Quick sanity check against a running VM: `ssh` in and confirm
  `/etc/deputyos/providers.json` exists and `systemctl status deputywizard` is
  `active`.
- **`Output directory 'build/packer-<target>' already exists. It must not
  exist.`** — Packer refuses to overwrite a prior bake's output dir. This
  bites when you force a re-bake by deleting `build/qemu-x86_64-<profile>.qcow2`
  (the Makefile's skip-gate file) to pick up new guest binaries: that
  removes the conforming-name file but not Packer's output dir.
  `build.sh` now passes `packer build -force` (commit b3b2480), so re-runs
  clobber the stale output — just re-run `make desktop-local-build`. On an
  older checkout without that fix, `rm -rf build/packer-qemu-x86_64` first.
- **First build is slow / needs network** — Packer fetches the base Debian
  image + apt packages during bake. Set `DEPUTYOS_VOICE_OFFLINE=1` to skip the
  voice-asset download if you don't need voice.

## How the agent reaches the local API

`deputyctl` reads `DEPUTYOS_API_BASE` from its process environment
(`deputyctl/src/{restore,backup,tunnel,audit}.rs`), defaulting to
`api.deputyos.com`. The image's systemd units source
`/etc/deputyos/secrets.env` via `EnvironmentFile=-/etc/deputyos/secrets.env`
(the gateways), and the `DefaultEnvironment` drop-in covers every other
service (the tunnel, the wizard). The seed writes both, then `runcmd` does
`systemctl daemon-reload` + a best-effort `try-restart` of the deputyos
services so already-booted units pick up the new env. `10.0.2.2` is the
canonical qemu user-mode-network host gateway — i.e. "your laptop" from
inside the VM. This is x86_64-specific (aarch64 qemu user-net uses a
different gateway); the loop is x86_64-first.
